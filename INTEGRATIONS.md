# Integrations reference

Verified capability reference for the publishing adapters and AI/MCP connections. All facts were checked against vendor pages on **2026-10-21** ("as checked 2026-10-21"). Anything not confirmed on an official source is marked **UNVERIFIED**. Vendor behavior changes fast: re-check before relying on a row, especially Hashnode and Medium.

This repo is public. Never commit credentials. All examples use placeholders such as `<your-token>`.

## 1. DEV.to (Forem API v1)

Sources (as checked 2026-10-21):
- https://developers.forem.com/api/v1 (official API reference)
- https://dev.to/morinaga/three-devto-api-behaviors-i-had-to-handle-explicitly-in-a-publish-pipeline-56c0 (community, for 429 behavior)

### Auth and headers

| Header | Value | Notes |
|---|---|---|
| `api-key` | `<your-devto-api-key>` | Official docs list `api-key` as the only authorization. Not `Authorization: Bearer`. |
| `Accept` | `application/vnd.forem.api-v1+json` | The official page only says an accept header is needed and does not print the value; the value comes from community write-ups. Without it you get v0 responses. |
| `Content-Type` | `application/json` | |

The key is generated by the user at dev.to, Settings, Extensions, "DEV Community API Keys".

### Create a draft

```http
POST https://dev.to/api/articles
api-key: <your-devto-api-key>
Accept: application/vnd.forem.api-v1+json
Content-Type: application/json

{
  "article": {
    "title": "<title>",
    "body_markdown": "<markdown, absolute image URLs>",
    "published": false,
    "canonical_url": "https://example.com/blog/<slug>",
    "tags": "tag1,tag2,tag3,tag4",
    "series": "<series name, created if missing>",
    "main_image": "https://example.com/cover.png",
    "description": "<short summary>",
    "organization_id": null
  }
}
```

Responses: `201` (article), `401`, `422`.

### Update, publish, unpublish

`PUT https://dev.to/api/articles/{id}` takes the same `article` object. Responses: `200`, `401`, `404`, `422`.
- Flip `published: true` only after the user approves in our UI.
- `published: false` on a live article reverts it to draft.
- The key must belong to the article's author.

### Field notes

| Field | Verified behavior |
|---|---|
| `published` | Default `false`, so omitting it gives a draft. |
| `tags` | Comma-separated string, "up to 4" (documented on POST). Community reports tags are lowercased and stripped of hyphens, and extras are silently dropped. |
| `series` | String; created if it does not exist. |
| `main_image` | Absolute URL of the cover. |
| `canonical_url` | For content originally published elsewhere. |
| `body_markdown` | Markdown with Liquid tags; may contain YAML front matter. Pick one source of truth: send JSON fields, no front matter. |

### Day 5 adapter check (as checked 2026-10-21)

Re-read from https://developers.forem.com/api/v1 before coding:
- Body fields for `POST /api/articles` and `PUT /api/articles/{id}`: `title`, `body_markdown`, `published` (default false), `series`, `main_image`, `canonical_url`, `description`, `tags` (typed as a string, "a comma-separated list of tags (up to 4 tags)"), `organization_id`. Responses 201/401/422 and 200/401/404/422.
- `GET /api/articles/me` (published), `/me/published`, `/me/unpublished`, `/me/all` take `page` and `per_page` (1 to 1000, default 30; the maximum can be lowered by the operator). The adapter reads 100 per page, up to 30 pages, and treats not found as "not found", not "never published".
- `GET /api/users/me` documents no response fields (the sample is empty). The adapter reads `username` and fails with a clear message if it is absent. UNVERIFIED which fields a real answer carries.
- The `Accept` value is still not printed on the official page; the adapter sends `application/vnd.forem.api-v1+json` as before.
- Tag characters and length limits are not documented. The adapter cleans to lower-case letters and digits and caps a name at 30 characters; both are our reading and are UNVERIFIED. It never drops a tag silently and blocks more than 4.
- A title limit (reported near 128 characters) is not documented; it is only a warning.
- No rate limit text was found. The adapter handles `429` with `Retry-After` in seconds or as an HTTP date and falls back to 30 seconds.

The adapter was exercised only against a local fake server and fake fetch functions. No real DEV.to request has been made.

### Gotchas
- **Rate limits are not documented** in the official reference (UNVERIFIED). Community reports ~10 article creates per 30 s and `429` with `Retry-After` as either seconds or an HTTP date. Parse both forms; fall back to 30 s.
- **No image upload endpoint** in the v1 reference (UNVERIFIED that none exists). Host images yourself and use absolute URLs.
- **Restrictions on API publishing:** none found in the API reference. DEV's AI-assisted content guidelines require disclosure of AI-assisted text (UNVERIFIED this run; see `docs/research/01-longform-platforms.md`). Treat as a per-adapter "disclosure line" option.
- Scheduling via the API is UNVERIFIED (it exists in the web editor).

## 2. Hashnode GraphQL API

Sources (as checked 2026-10-21):
- https://hashnode.com/announcements/graphql-api (official, dated 2026-05-13)
- https://hashnode.com/pro (official pricing)
- https://github.com/Hashnode/gql-skill (official agent skill; includes `schema.graphql`, `mutations.md`, `auth-and-roles.md`, `errors-and-limits.md`)
- https://hashnode.com/blog/hashnode-mcp-server and https://hashnode.com/blog/hashnode-cli (official)

### Endpoint and auth

| Item | Value |
|---|---|
| Endpoint | `POST https://gql-beta.hashnode.com/` (official skill). `https://gql.hashnode.com` returned a 301 to the deprecation announcement on 2026-10-21. Make the host a config value. |
| Auth | `Authorization: Bearer <your-hashnode-pat>`. The `Bearer ` prefix is optional and case-insensitive per the official skill. |
| Token source | Hashnode, Account Settings, Developer, generate a personal access token. |
| Extra header | The official skill asks callers to send an `x-hashnode-client` identifying header. Optional, not a secret. |
| Pro requirement | The 2026-05-13 announcement: "Every API request, queries and mutations, now requires a Pro plan on your publication." The skill README is softer (public reads free, writes and publication-scoped reads need Pro). **Plan on Pro for any write.** The two statements conflict on public reads: UNVERIFIED which is current. |
| Price | Pro is $5 per month or $50 per year, per publication. Payment is something the user does themselves. |
| Failure mode | Writes on a non-Pro publication return `FORBIDDEN` with a message about the Pro plan. Do not retry; surface "upgrade needed" in the UI. |
| Image upload | `createImageUploadURL` and `confirmImageUpload` need auth but are not Pro-gated (8 MB, `image/*`, no SVG). |

### Mutations (verified in the official schema)

| Mutation | Input | Notes |
|---|---|---|
| `createDraft` | `CreateDraftInput!` | Returns `draft`. |
| `updateDraft` | `UpdateDraftInput!` | Takes `draftId`. |
| `publishDraft` | `PublishDraftInput!` | Takes only `draftId`; returns `post`. Goes live immediately. |
| `publishPost` | `PublishPostInput!` | Publishes directly. Avoid: it skips the draft gate. |
| `updatePost`, `deleteDraft`, `submitDraftForReview` | | Contributors cannot publish; they use `submitDraftForReview`. |

`CreateDraftInput` fields relevant to us: `publicationId` (required `ObjectId`), `title`, `subtitle`, `contentMarkdown`, `slug`, `tags: [{ slug, name }]` (max **15**, new tags are created), `seriesId`, `originalArticleURL` (canonical), `publishedAt` (backdating), `coverImageOptions { coverImageURL }`, `settings`, `metaTags`, `disableComments`.

```bash
curl -s https://gql-beta.hashnode.com/ \
  -H "Authorization: Bearer $HASHNODE_PAT" \
  -H "Content-Type: application/json" \
  -d '{
    "query": "mutation($input: CreateDraftInput!){ createDraft(input:$input){ draft { id slug } } }",
    "variables": { "input": {
      "publicationId": "<publication-id>",
      "title": "<title>",
      "contentMarkdown": "<markdown>",
      "originalArticleURL": "https://example.com/blog/<slug>",
      "tags": [{ "slug": "typescript", "name": "TypeScript" }],
      "coverImageOptions": { "coverImageURL": "https://example.com/cover.png" }
    } }
  }'
```

Then, after user approval only: `mutation($input: PublishDraftInput!){ publishDraft(input:$input){ post { id url } } }` with `{ "input": { "draftId": "<draft-id>" } }`.

### Limits (official `errors-and-limits.md`)

| Limit | Value |
|---|---|
| Tags per post or draft | 15 |
| Request body | 100 KB (long articles with inline content may need chunked image hosting) |
| Query depth | 10 |
| Rate limit | Published targets 20,000 queries/min and 500 mutations/min, **not currently enforced**. Do not build logic around it. |
| Caching | Query responses may be cached ~25 s; read-after-write can be stale. |

### Day 5 adapter check (as checked 2026-10-21)

Read from the official agent skill (https://github.com/Hashnode/gql-skill: `SKILL.md`, and in `skills/gql-api/references/`: `schema.graphql`, `queries.md`, `mutations.md`, `auth-and-roles.md`, `errors-and-limits.md`, `recipes.md`):
- Endpoint `https://gql-beta.hashnode.com/`, `Authorization: Bearer <pat>`, and the skill asks for an `x-hashnode-client` header (the adapter sends `brand-os`).
- `me { id username name publications(first: Int!, after: String) { edges { node { id title url isTeam } } } }` finds the account and the publication ids. `me` needs authentication; the documents do not say it needs Pro.
- `createDraft(input: CreateDraftInput!)` takes `publicationId`, `title`, `contentMarkdown`, `tags: [{ slug, name? }]` (max 15), `originalArticleURL`, `coverImageOptions { coverImageURL }`, `metaTags { title, description, image }`, `seriesId`. `updateDraft(input: UpdateDraftInput!)` takes the same fields keyed by `draftId` (no `publicationId`). `publishDraft(input: { draftId })` returns `post { id slug url }` and soft-deletes the draft. All three need a Pro plan; the non-Pro answer is `FORBIDDEN` with a message about the Pro plan.
- `draft(id: ObjectId!)` and `post(id: ID!)` and `publication(id:) { posts(first:) }` are the read paths. A caller not allowed to see a draft gets `NOT_FOUND`, not `FORBIDDEN`.
- Errors are in `errors[].extensions.code`: `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `BAD_USER_INPUT`, `INTERNAL_SERVER_ERROR`. The documents do not say which HTTP status accompanies them; the adapter handles both HTTP errors and 200 with `errors`.
- Limits: 100 KB request body, 15 tags, 8 MB images (no SVG). The rate limit is advisory.

UNVERIFIED and therefore live-unverified: the real HTTP status of each error code; whether `updateDraft` accepts a payload identical to the current one; the draft preview address (the adapter shows no private link); series (needs an existing series id, so the series is ignored with a warning); how a published draft is found afterwards (the adapter looks for the post by title and canonical URL among the 20 newest posts). The adapter was exercised only against a local fake of the schema. No real Hashnode request has been made.

### Gotchas
- GraphQL returns HTTP 200 with an `errors[]` array. Check `errors[].extensions.code` (`UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `BAD_USER_INPUT`).
- `publicationId` is not the blog slug. Get it from `me { publications(first: 10) { edges { node { id } } } }`.
- Series creation is not verified here: `seriesId` needs an existing series (look up via a series query; UNVERIFIED which query).
- Hashnode's official MCP (`https://mcp.hashnode.com/mcp`, browser login, no token) has draft tools (`create_draft`, `update_draft`, `publish_draft`) but the announcement does not say whether they accept a canonical URL. UNVERIFIED. The app should use GraphQL, not the MCP, for adapters.
- The official CLI (`@hashnode/cli`) documents `--original-article-url` under `post create`; whether `draft create` accepts it is UNVERIFIED.
- Free fallback (no Pro): manual copy-assist. In the Hashnode editor, Draft Settings, "Are you republishing?", Add Original URL (see `docs/research/01-longform-platforms.md`; not re-checked this run).

### What is automatable

| Path | New user? | Automatable by the app? |
|---|---|---|
| Integration token plus `POST /v1/users/{id}/posts` | No: "Medium will not be issuing any new integration tokens for our API and will not allow any new integrations." | Only for a user who already holds a token from before the cutoff (community sources say 2025-01-01, UNVERIFIED). "All existing tokens will continue to work." |
| Import tool (Stories, Import a story, paste URL) | Yes | **No.** It is a signed-in web UI action. The app prepares a fix-up kit; the user runs it. |
| Browser automation of the editor | Technically possible | **Do not build.** Medium Rules prohibit using "any software, script, robot ... (including crawlers, browser plugins and add-ons ...)" to access the services and posting "automatically, systematically, or programmatically". |

The API repo README states "The Medium API is no longer supported" and the repo was archived 2023-03-02. Whether `POST /v1/users/{id}/posts` still works for an old token is UNVERIFIED this run (no token to test with); only the help page statement that old tokens keep working is verified.

### Legacy API shape (for users who already have a token)

```http
POST https://api.medium.com/v1/users/<user-id>/posts
Authorization: Bearer <your-medium-integration-token>
Content-Type: application/json

{
  "title": "<title>",
  "contentFormat": "markdown",
  "content": "<markdown>",
  "canonicalUrl": "https://example.com/blog/<slug>",
  "tags": ["a", "b", "c"],
  "publishStatus": "draft"
}
```

From the archived README: `publishStatus` is `public`, `draft` or `unlisted` (default `public`, so always send `draft`); only the first 3 tags are used; titles over 100 characters are ignored; response `201` with a `data` envelope.

### Import tool (the supported path)

1. Medium, Stories, "Import a story", paste the canonical URL, Import, "See your story".
2. The story arrives as an editable draft, backdated, with a **canonical URL applied automatically** ("Imported stories will automatically apply a canonical URL referencing the original source material").
3. The user edits and clicks Publish. Only import content you have the right to import.

If import fails, Medium says to move the content manually (help article 360033931713, not re-fetched). Import fidelity for tables, SVG, and custom components is UNVERIFIED; plan PNG substitutes.

### Policy points
- Cross-posting your own blog content is allowed; "clipped" teasers whose purpose is linking out count as spam. Post the full article.
- Medium's AI-content disclosure rules were checked on 2026-10-19 (`docs/research/01-longform-platforms.md`) and not re-fetched.

### Day 4 adapter check (as checked 2026-10-21)

Sources: https://docs.ollama.com/api/openai-compatibility and https://docs.ollama.com/api/chat (both fetched). https://platform.openai.com/docs/api-reference/chat/create returned HTTP 403 to the automated fetch, so **OpenAI's own request and response reference was not read this run: UNVERIFIED against openai.com**.

What the adapter (`apps/web/src/server/ai/adapters/openai-compatible.ts`) relies on:
- Ollama's compatibility page lists `/v1/chat/completions` with `model`, `messages`, `max_tokens`, `temperature`, `response_format`, `seed`, `stop`, `stream`, `stream_options` (`include_usage` only), `tools`; it does not support `tool_choice`, `logit_bias`, `user`, `n` or logprobs. The page does not describe the response object. The adapter reads the widely implemented shape `choices[0].message.content` and `usage.prompt_tokens` and `usage.completion_tokens`, and treats missing usage as unknown (it then estimates and says so).
- The adapter sends `max_tokens` first. Newer OpenAI models reject it in favour of `max_completion_tokens` (UNVERIFIED here, from common behaviour); if a 400 names both, it retries once with the other. Other servers only know `max_tokens`.
- The key header is always sent (`Authorization: Bearer`), with a placeholder when none is set, because Ollama requires a non-empty value and ignores it locally.
- Ollama's native `/api/chat` has `format` (a JSON schema) and returns `prompt_eval_count` and `eval_count`; the adapter does not use it. Structured output is enforced by our own validation of the returned text, not by `response_format`, so a server that ignores `response_format` still works. The behaviour for a missing model (status code and body) is not documented on those pages: UNVERIFIED, shown to the person as whatever the server says, with keys removed.

### Generic OpenAI-compatible servers (LM Studio, vLLM, llama.cpp server, hosted gateways)
Model the connection as `{ baseUrl, apiKey?, model }`. Do not assume feature parity: probe `GET /v1/models` on connect, and capability-test streaming, tools, and `response_format` once, storing the result per connection. The app must also work with **no** model configured (see section 7).

```bash
  -H "content-type: application/json" \

```

### Billing and key handling
- Usage bills to the organization that owns the key (the user's Console account), at the user's own rate limits and spend limits. The app has no Anthropic bill of its own.
- Key types (personal, service account, workspace) are chosen by the user in the Console. The docs recommend a secrets manager, rotation, and disabling leaked keys.
- Multi-tenant rules for this app: store each key per user, encrypted at rest with an app-level key; show only the last 4 characters after saving; never write it to logs, error reports, analytics, or prompts; redact `x-api-key` and `Authorization` in any HTTP debug output; send it only to `api.anthropic.com`.
- Anthropic's Claude Code legal page (section 7) says hosts may not pay for or intermediate Claude usage on behalf of end users; BYOK keeps the app compliant.

### Day 4 adapter check (as checked 2026-10-21)

Sources: https://platform.claude.com/docs/en/api/overview, https://platform.claude.com/docs/en/api/errors, https://platform.claude.com/docs/en/api/messages (first 100,000 of 1.2 million characters read, which covered the request fields), https://platform.claude.com/docs/en/models/overview.

Verified and used by `apps/web/src/server/ai/adapters/anthropic.ts`:
- `POST https://api.anthropic.com/v1/messages` with `model`, `max_tokens`, `system` (a top-level field; there is no system message role) and `messages`. Required headers: `anthropic-version` (the overview lists `2023-06-01` and marks it required), `content-type`, and an auth header. The overview says `Authorization: Bearer <key>` is the primary form and `x-api-key` is a legacy fallback "still supported"; the adapter sends `x-api-key` (the form in the official curl examples) and the header is set in one place.
- `anthropic-workspace-id` is required with a multi-workspace key and optional otherwise; it is an optional field in the provider form.
- Success: a `content` array of blocks (a `thinking` block can come before the `text` block; only text blocks are read), `stop_reason` (`max_tokens` means the text may be cut off, `refusal` is treated as no answer) and `usage.input_tokens` and `usage.output_tokens`.
- Errors are JSON `{ "type": "error", "error": { "type", "message" }, "request_id" }` with 400 (also used when a spend limit is reached), 401, 402, 403, 404, 409, 413, 429 (a spend-cap 429 has no `retry-after`), 500, 504 and 529 (overloaded). The adapter retries 429 (when `retry-after` is short), 500 and 529 once and nothing else.
- Models: `claude-sonnet-5-5` and `claude-haiku-5-5` are listed as current ids on the models overview; both use adaptive thinking. Sonnet 5.5 refuses `thinking: {"type": "disabled"}`, so the adapter sends no `thinking` field at all and a generous `max_tokens` (8000) so thinking cannot starve the answer. These are suggestions in the form (a free-text field); the app never requires a model id to match.

## 6. Connecting the user's own Claude Code to our MCP server

Sources (as checked 2026-10-21):
- https://code.claude.com/docs/en/mcp
- https://modelcontextprotocol.io/specification/latest/basic/authorization (page content is spec revision **2026-07-28**)

### 6a. Local server over stdio

```bash
claude mcp add [options] <name> -- <command> [args...]
claude mcp add --env CPH_API_URL=http://127.0.0.1:3100 --transport stdio content-powerhouse \
  -- node /path/to/mcp-server.js
```

- Everything after `--` goes to the server unchanged. `--env` takes `KEY=value` pairs; put another option (for example `--transport stdio`) between `--env` and the server name or the name is read as another pair.
- Scopes: `local` (default, stored in `~/.claude.json`), `project` (shared, `.mcp.json` in the repo root), `user` (all projects). Choose with `--scope`.
- Project scope file, with env expansion (`${VAR}` and `${VAR:-default}` work in `command`, `args`, `env`, `url`, `headers`):

```json
{
  "mcpServers": {
    "content-powerhouse": {
      "type": "stdio",
      "command": "node",
      "args": ["./mcp/server.js"],
      "env": { "CPH_API_URL": "${CPH_API_URL:-http://127.0.0.1:3100}" }
    }
  }
}
```

- Interactive sessions ask the user to approve servers from `.mcp.json` before use (reset with `claude mcp reset-project-choices`). Do not put secrets in a committed `.mcp.json`; reference env vars.
- **Windows:** the current MCP docs page no longer contains a `cmd /c npx` note (a search of the page found none). Community issues from 2026 say native Windows may still need `cmd /c npx -y <package>` because `npx` is a `.cmd` shim, and that `claude mcp add` has mangled the `/c` flag in some versions (issues reported closed). Status: **UNVERIFIED**. Safest for our server: use `node <path>` directly (no shim), or `npx` via `cmd /c` and check `claude mcp get <name>` to confirm `/c` was stored intact; fall back to editing the config entry so `command` is `cmd` and `args` starts with `["/c", "npx", ...]`.
- stdio servers should not follow the MCP OAuth spec; the spec says stdio "SHOULD NOT" use it and should take credentials from the environment.

### 6a-2. The `brand-os` server (Day 4)

`packages/brand-mcp` is registered the same way as any stdio server. Registration for this repo (a command the owner runs; do not run it from an agent): `claude mcp add --scope project --transport stdio brand-os -- node "<repo>/packages/brand-mcp/dist/index.js"`, then forward `BRAND_OS_CREDENTIAL` and `BRAND_OS_URL` through `.mcp.json` with `${VAR}` expansion (documented above) so no secret is stored in a file. Full steps, scopes and troubleshooting: `docs/brand-os-mcp.md`. The Windows `npx` shim question is avoided by calling `node` on the built file directly.

### 6b. Hosted server over streamable HTTP

```bash
claude mcp add --transport http content-powerhouse https://<your-host>/mcp
claude mcp add --transport http content-powerhouse https://<your-host>/mcp \
  --header "Authorization: Bearer <your-cph-token>"
```

- `sse` transport is deprecated; use HTTP.
- **Header auth:** simplest for self-hosters. Per-user personal access tokens issued by the app, sent as `Authorization: Bearer ...`. In `.mcp.json` use `"headers": { "Authorization": "Bearer ${CPH_TOKEN}" }`. If the server rejects a configured header, Claude Code reports the connection as failed and does not fall back to OAuth.
- **OAuth:** the user runs `/mcp` in Claude Code (or `claude mcp login <name>`) and completes the browser flow; tokens are stored and refreshed by Claude Code. If the server has no Dynamic Client Registration use `--client-id`, `--client-secret` (prompted) and `--callback-port <port>`; redirect form is `http://localhost:PORT/callback`. `claude -p` runs cannot start OAuth, so the user must sign in interactively first.
- **Current MCP spec requirements for an HTTP server (revision 2026-07-28):**
  - OAuth 2.1 with PKCE; authorization is optional overall, but HTTP servers that use it SHOULD follow the spec.
  - The MCP server MUST implement Protected Resource Metadata (RFC 9728); clients MUST use it for authorization server discovery. The authorization server MUST offer RFC 8414 or OpenID Connect discovery.
  - Client registration: Client ID Metadata Documents SHOULD be supported; Dynamic Client Registration is **deprecated** and kept for compatibility; pre-registered clients are allowed.
  - Clients MUST send the RFC 8707 `resource` parameter in authorization and token requests; servers MUST validate that tokens were issued for them (audience) and MUST NOT pass tokens through to other services.
  - Bearer token in the `Authorization` header on every request; never in the query string. 401 for missing or invalid tokens, 403 for insufficient scope with `WWW-Authenticate`.
- Local HTTP servers must validate the `Origin` header and bind to 127.0.0.1 (from the Streamable HTTP transport spec; carried over from `docs/research/06-connect-ux-and-architecture.md`, not re-fetched).
- Tool design: Claude Code defers MCP tool definitions by default (tool search), truncates server instructions and descriptions at 4,096 characters, and honors the tool annotation `_meta["anthropic/requiresUserInteraction"] = true` to force a permission prompt on every call. Use that annotation on the `publish` tool.
- Remote servers added in claude.ai web are called from Anthropic's cloud and must be publicly reachable; a localhost server works from Claude Code and Claude Desktop only.

## 7. User-driven Claude Code use vs automatic API inference

### The rules for this app

| Scenario | Who runs inference | Whose terms and billing | What the app does |
|---|---|---|---|
| **A. User runs their own Claude Code against our MCP server** | The model inside the user's Claude Code session | The user's own Claude subscription or API key, under their own agreement with Anthropic | Exposes tools and data only (list drafts, read content, preview adaptation, stage a draft, request approval). Makes no model call, holds no Claude credential. |
| **B. BYOK** | Our server calls `api.anthropic.com` with the user's key | The user's Console account is billed | Stores the user's API key (encrypted, per user, never logged) and uses it only for features the user explicitly triggers. |
| **C. Local model** | Ollama or another OpenAI-compatible server the user runs | The user's hardware | Calls the configured base URL. |
| **D. No AI** | Nothing | n/a | Every feature must work: manual editing, rule-based adaptation (template and formatting transforms), manual approval, and publishing. |

Hard requirements:
1. **No feature may require AI.** AI is an optional accelerator behind a "model provider" setting that can be empty.
2. **The app never calls Anthropic** unless the user has saved their own API key (B). No default key, no shared key, no fallback to a key owned by the operator.
3. **The app never asks for, accepts, or stores a Claude login** (email and password, session cookie, `claude.ai` OAuth token, or a token pulled from Claude Code's credential store). Accept an **API key only**. Do not read `~/.claude` credentials.
4. The app must not launch the `claude` binary with the user's subscription on a hosted server, and must not proxy a user's subscription traffic. User-driven Claude Code (A) happens on the user's machine, outside the app.
5. Publishing actions stay behind explicit user approval regardless of which AI path produced the content.

### Policy check (as checked 2026-10-21): VERIFIED

Source: https://code.claude.com/docs/en/legal-and-compliance, section "Authentication and credential use". Key statements:
- OAuth authentication "is intended exclusively for purchasers of Claude Free, Pro, Max, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications."
- "Developers building products or services that interact with Claude's capabilities ... should use API key authentication through Claude Console or a supported cloud provider."
- Anthropic "does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users", and developers "may not collect, store, or intermediate Claude.ai credentials or session tokens".
- Not restricted: customers configuring their own API keys, and an end user signing in to the **unmodified Claude Code binary** with their own subscription.
- Related: "Customers may not pay for, resell, or intermediate Claude usage on their end users' behalf"; each end user authenticates with their own key or plan. Advertised Pro and Max limits "assume ordinary, individual usage of Claude Code and the Agent SDK."

Reading for this app: scenario A (the user's own Claude Code calling our MCP tools) is the user using the unmodified Claude Code binary themselves, so our app is only an MCP tool provider. Scenario B (BYOK API key) is explicitly allowed. Any design that logs a user into Claude from inside the app, or runs Claude Code on the operator's server using a user's subscription, is not allowed. This is a reading of the cited policy, not legal advice; for edge cases Anthropic points to its sales contact.

Wording rule for the UI: never say "Connect your Claude account". Say "Add an Anthropic API key (optional)" and "Use Claude Code on your own machine (optional)".
